# Release publishing, promotion and rollback

SynFactory releases are promoted by immutable OCI digests. A mutable branch or image tag is never a deployment input.

## Release contract

A publish operation requires all of the following:

- an explicit release version;
- the exact 40-character source commit SHA from `develop`;
- the complete `release-bundle-<source-sha>` artifact generated by the successful `develop` CI run for that exact source;
- `release_ready: true` and all required security gates marked `passed` in its evidence manifest;
- recorded scanner versions, control/worker/web image archive identities and CycloneDX SBOM paths plus hashes;
- an OCI repository prefix;
- a durable release-manifest output path.

PR CI still retains lightweight evidence metadata/SBOMs for review, but marks it `release_ready: false` and does not retain image archives. Only a successful CI run for a pushed `develop` commit exports the exact scanned images and produces a short-lived release-ready bundle. This avoids storing large duplicate image archives for every PR head while ensuring a published release comes from the integration branch.

The raw retained evidence manifest is SHA-256 fingerprinted when loaded. That fingerprint, scanner versions, optional web lock hash, SBOM paths/hashes and registry digests are retained in the release manifest and participate in its deterministic release ID. This provides a direct trace from a deployed digest back to the exact gated `develop` source and exact scanned image artifacts.

The release command refuses PR-only evidence, a different source SHA, missing scanner provenance, a failed/missing security gate, unsafe artifact paths, an invalid image/SBOM identity, a tampered image archive, a loaded image ID that differs from the gated evidence, or a registry response that does not contain an immutable `sha256` digest.

## Registry authentication

Authentication is intentionally outside the release manifest and command arguments. Authenticate the local Docker client before publishing with the registry's least-privilege push credential. Prefer short-lived credentials and `--password-stdin`; never place passwords/tokens in Docker build arguments, image labels, shell history, release evidence or committed files.

For GHCR, for example, use a token with only the package permissions required by the target repository and authenticate with `docker login ghcr.io --username <user> --password-stdin`. Other OCI registries work through the same Docker registry adapter.

## Publish

After the selected change is squash-merged, wait for the CI run on that resulting `develop` commit to complete successfully, then download and extract `release-bundle-<source-sha>` preserving its `release-evidence/` layout. Run the release command from a checkout of that exact `develop` SHA. The command requires `git rev-parse HEAD` to equal the source SHA, validates every image archive hash before loading it, then verifies the loaded Docker image ID equals the identity scanned by CI. It does not rebuild or rescan an image during publishing.

```sh
go run ./cmd/synfactory-release publish \
  --version v1.0.0 \
  --source-sha <exact-develop-40-char-sha> \
  --evidence release-evidence/manifest.json \
  --registry ghcr.io/<owner>/synfactory \
  --output releases/v1.0.0.json
```

For each evidence-bound image, publishing uses a deterministic immutable tag derived from the release version, source SHA and gated local image identity. The command captures the registry-returned digest and writes one manifest binding version, source SHA, evidence fingerprint, scanner metadata, repository digest and SBOM provenance. Deployments never consume the tag; they consume only the captured digest.

The durable output path is also the local idempotency record. If it already contains the same version/source/evidence/scanner/repository/SBOM identity, rerunning publish returns without loading artifacts or mutating the registry. If that path is already bound to different release evidence, publishing fails before any registry call. Keep canonical release manifests at a single predictable path such as `releases/<version>.json`; registries used for production should additionally enable immutable tags where supported.

The lightweight metadata evidence is retained for 30 days. The larger release-ready bundle is retained for 7 days because it is needed only until the exact images have been published to the OCI registry; after publication, the durable release manifest and registry digests are the promotion/rollback source of truth.

Transient network/registry failures are retried a bounded number of times; authentication, policy and malformed-digest failures are not retried.

## Promote

Promotion consumes an existing release manifest and emits only digest-qualified image references.

```sh
go run ./cmd/synfactory-release promote \
  --manifest releases/v1.0.0.json \
  --environment staging \
  --output deployments/staging.json
```

Every image in the resulting document is `repository@sha256:<digest>`. Deployment automation must consume these digest references directly and must not rebuild source or resolve a mutable tag during promotion.

## Rollback

Rollback is promotion of a previously retained known-good release manifest. It does not rebuild old source.

```sh
go run ./cmd/synfactory-release rollback \
  --manifest releases/v0.9.4.json \
  --environment production \
  --output deployments/production.json
```

Keep release manifests and their metadata evidence for the retention period required by operations. A rollback candidate is valid only when its manifest validates and its referenced registry digests remain available.

## Failure policy

Registry authentication and policy failures are permanent for the current invocation and require operator/configuration correction. Timeouts, connection resets, temporary DNS/network failures, HTTP 429 and registry 5xx responses are transient and receive bounded retry with backoff. Exhausted retries stop the publish; security/evidence checks are never weakened or bypassed to make a release succeed.
