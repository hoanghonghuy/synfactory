# Authentication and authorization

SynFactory keeps authentication and authorization in the Go control plane. Vue, agents, runtime providers and external identity providers never become authorization truth.

## Identity model

A named user is identified by a stable SynFactory user ID and an external `(provider, provider_subject)` identity. External provider access/refresh tokens are provider credentials and must not be copied into normal evidence, API responses or authorization audit payloads.

Authorization is composed from:

- role grants: `administrator`, `operator`, `reviewer`, `observer`;
- optional repository scope on each role grant;
- explicit sensitive permission grants for terminal access, release promotion and security-policy changes.

`operator` grants ordinary read and repository mutation only. Terminal, release and security-policy authority are not inherited from the operator role. `reviewer` and `observer` are read-only by default. `administrator` is the explicit break-glass role and therefore has all permissions.

## Sessions

Browser/API sessions use opaque bearer values generated by the server. Only a SHA-256 token hash is durable. Session records have explicit expiry and optional revocation timestamps; expired or revoked sessions fail closed. Authorization decisions are auditable by user/session/permission/repository/result without storing the bearer value.

The session TTL is bounded by Go policy. Provider authentication may establish identity, but it does not choose roles or sensitive permissions.

## OIDC/OAuth provider contract

Provider integration must terminate in a provider-neutral identity result containing the provider name, immutable provider subject and safe display metadata. Provider-specific claims may assist login, but repository roles and sensitive permissions come from SynFactory policy/storage rather than arbitrary provider claims unless an explicit trusted mapping policy is configured.

Initial GitHub login support may be added as an adapter. The core authorization/session contracts must remain usable by other OIDC/OAuth providers.

## Legacy operator-token migration

The existing `SYNFACTORY_OPERATOR_TOKEN` mode remains an explicit compatibility mode for simple self-hosted deployments while multi-user authentication is introduced.

During the compatibility period:

1. the legacy bearer token maps to one synthetic `legacy-operator-token` administrator principal;
2. it never creates a named-user identity implicitly;
3. session/OIDC and legacy authorization must share the same Go-owned permission checks at protected API boundaries;
4. mixed mode must be explicit in configuration rather than inferred from whichever credential happens to arrive;
5. disabling legacy mode must make legacy credentials fail closed without invalidating named-user session state.

Legacy mode may be deprecated only after login/session/bootstrap operations are documented and production deployments have a deterministic migration path. It must not be silently removed or silently remain as an undocumented bypass.

## API integration rules

- Read endpoints require `read` authority and must respect repository scope when repository data is involved.
- Repository mutations require `repository_mutate` for the target repository.
- Terminal endpoints require `terminal_access`; ordinary operator/read authority is insufficient.
- Release promotion requires `release_promote`.
- Security-policy mutation requires `security_policy`.
- Authorization is re-evaluated at the Go API boundary; hiding a button in Vue is never a security control.
- Session revocation/expiry and grant changes must take effect deterministically without requiring a browser refresh to become authoritative.
